# 中文注释覆盖与维护

目标分支：`learning/full-chain-study-bay`。目标是能顺着源码理解整个项目的逻辑，同时在实际用法中学习 TypeScript。注释直接解释代码，不加“中文学习”等前缀。

完整目标包括手写源码、测试、示例、构建脚本和其他语言的实现。阶段性完成某个包，不代表其他包已经完成；只解释了文件中的一条调用链，也不算整份文件完成。

## 注释的完成条件

- 文件开头解释它负责什么、上游如何进入、结果流向哪里。
- 函数前解释用途、输入、输出、副作用、错误、主要流程，给一个小例子。例子必须符合实际签名，不用过时 API。
- 函数内逐条解释有意义的源码行，覆盖分支、异步、回调、状态变化和错误路径；同时结合当前代码解释类型、泛型、解构、展开、收窄等语法。
- 类型和字段解释业务含义，区分编译期类型检查与运行时校验。
- 纯闭括号由所属结构说明，不为凑行数添加重复的“结束”注释。多行字符串中的文字仍属于运行时输入/输出，不能往其中插入注释。
- 原英语文档保留，代码表达式、类型、导出、默认值和模型提示词保持一致。注释不能把“请求取消”写成“已经停止所有操作”等不存在的保证。
- 完整读过并核对调用关系；只看到中文或注释很多，不足以标记完成。

生成的目录数据、模型包装器、版本同步文件和第三方代码不手改。在对应生成入口解释它们的来源和用法。JSON 等不允许注释的格式通过旁边说明解释，不能改成另一种格式后声称只是注释。

## 查看当前覆盖

```sh
# 汇总完整/部分/待处理/需复核文件数。
node scripts/study-status.mjs

# 列出整个仓库的逐文件状态，包含未复核过的新文件。
node scripts/study-status.mjs --files
```

[study-coverage.json](study-coverage.json) 只记录已经人工复核过的文件；未列出的手写文件为 `pending`。生成或第三方来源文件标为 `reference`，不计为已经完整注释。

默认的 `reference` 根据文件名、文件头的来源标记和明确的版本同步入口初筛；仍需核对实际生成器或第三方来源，不能把自动分类当成已经读懂该文件。

| 状态 | 含义 |
| --- | --- |
| `complete` | 该文件按上面的条件完成了整文件注释和复核 |
| `partial` | 只有部分函数或某条调用链已注释，仍有明确缺口 |
| `pending` | 尚未复核，不推断它没有任何中文，也不推断它已经能独立读懂 |
| `stale` | 已记录的文件内容发生变化，必须重新核对；可能是逻辑、类型、注释或格式变化 |
| `reference` | 生成/第三方来源入口，应解释来源，保留产物本身 |

脚本比较整份文件的 SHA-256，不试图猜测注释语义。它会把空格或注释修改也标成变化，宁可让人确认，也不把类型变化悄悄漏掉。没有 `stale` 只说明复核记录与文件内容一致，不保证注释结论正确。

指纹按单文件保存。被调用函数或类型定义改变时，调用方自身可能没改，但对它的解释已经需要更新；这类间接影响要结合上游 diff 和调用关系人工复核，脚本不会自动推导。

## 合并 main 后如何维护

先提交自己的工作，再按日常 Git 流程获取并合并上游；本轮不会自动替你合并 `main`。

```sh
git fetch origin main
git merge origin/main
node scripts/study-status.mjs
```

1. 阅读上游实际改动和 `stale` 文件全文，核对函数签名、调用方、状态/错误分支、例子和类型说明。冲突不能简单选 ours 或 theirs 掩盖上游逻辑。
2. 检查新文件、移走的文件和生成入口；文件改名后，旧的复核记录应移到实际路径并重新核对。
3. 更新解释、学习导航和相应例子；只改了少数函数的文件仍保持 `partial`。
4. 运行仓库要求的 `npm run check`，以及与上游业务变动对应的测试。仅注释改动可比较前后去注释的 JS 输出；这不能替代类型变化或真实功能变更的验证。
5. 通过检查后，更新复核记录中的文件字节指纹，在 [学习日志](STUDY_LOG.md) 记录真实复核的上游提交、范围、结果及尚未解决的问题。不要仅刷新指纹就算语义复核。

例如复核完 `packages/agent/src/agent.ts` 后，可以获取当前字节指纹：

```sh
shasum -a 256 packages/agent/src/agent.ts
```

将输出的 64 个十六进制字符（256 位）填入 `study-coverage.json` 对应文件的 `sha256`；`status` 依据整文件覆盖情况选 `complete` 或 `partial`，`note` 写剩余缺口或本次核对范围。文件改名时同步改键名。新文件应读完、核对并加注释后才新增记录。`baselineCommit` 记录本批对照起点，实际合入的上游提交另在日志中写清楚。

多代理按不重叠文件集处理。完成后统一检查、汇总和更新指纹，避免一个代理的格式化打断另一个代理的编辑。
